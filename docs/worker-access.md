# 작업자 링크 접근 (로그인 없는 진입)

작업자가 계정을 만들거나 앱을 설치하지 않아도 배정된 작업지시를 열고 TBM·점검을 수행할 수 있게
하는 구조다. 현장 작업자는 교체가 잦고 기기도 제각각이라 "설치·로그인 후 사용"을 전제하면
도입 자체가 막힌다. 그래서 **설치와 로그인을 전제하지 않는 것**을 기본값으로 둔다.

관련 코드: `src/server/worker-access.ts`, `db/0011_work_order_access_grants.sql`,
`src/app/w/` (진입·화면), `src/features/inspections/actions.ts` (제출 권한)

## 동선

```
작업지시 발급
  → work_order_access_grants 행 생성 (작업지시 × 발급회차 × 작업자)
  → 행마다 토큰 발급 (배정별 1개)
  → 메일(무료) · 메일+알림톡(유료) 로 https://smbe.net/w/<토큰> 전달
  → 작업자가 링크 탭
  → 서버가 토큰으로 행 조회 → 이름 표시 → 확인
  → inspections.entry_path = 'LINK' 로 기록
```

전달 채널은 토큰과 무관하다. 같은 토큰이 메일로도 알림톡으로도 나간다. 요금제는 **채널만** 가른다.
채널 설계(알림톡 + SMS 대체발송)와 데이터 모델 정리는 [notifications.md](notifications.md)에 있다.

## 설계 결정과 근거

### 토큰에 정보를 담지 않는다

JWT처럼 이름·소속을 토큰에 서명해 넣는 방식을 쓰지 않는다.

- base64는 암호화가 아니라 인코딩이다. 이름이 문자 본문·서버 로그·브라우저 히스토리에 평문으로 남는다
- 서명 토큰은 만료 전까지 폐기할 수 없다. 오발송·작업자 교체에 대응할 수단이 사라진다
- 길이가 길어져 SMS 90바이트를 넘긴다 (LMS 전환 = 단가 3배)

토큰은 **임의 문자열 포인터**이고 정보는 전부 DB에 있다.

### 배정별 1개, 공용 링크 없음

작업지시당 공용 링크 하나를 쓰면 "누가 TBM을 확인했는가"가 기록되지 않는다. 안전관리에서
이 기록이 증빙의 본체이므로 공용 링크는 선택지가 아니다. `work_order_access_grants`가
`UNIQUE(work_order_id, issue_version, user_id)`로 배정 단위를 강제하고, 토큰을 여기 1:1로 붙인다.

### 발송 기록과 분리한다

토큰은 **접근 권한**이고 `work_order_outputs`는 **발송 기록**이다. 유료는 같은 작업자에게 메일과
알림톡을 모두 보내므로 발송 기록은 채널별로 행이 나뉘지만, 토큰은 채널 수만큼 복제되면 안 된다.
메일로 가든 알림톡으로 가든 같은 링크여야 열람 집계가 하나로 모이기 때문이다.

0010은 토큰을 outputs 에 붙였다가 0011에서 분리했다. 채널이 하나라고 가정한 설계였다.

### 원문 대신 해시를 저장한다

`access_token_hash`에 sha256 hex만 보관한다. DB가 유출돼도 링크를 되살릴 수 없다.
발급 시 반환되는 평문이 유일한 사본이다.

> 기존 `company_invitations.token`은 평문 저장이다. 그쪽은 링크만으로 권한이 생기지 않고
> 로그인을 거치므로 성격이 다르지만, 정리 대상으로 남겨둔다.

### 길이: 16바이트 (base64url 22자)

128비트면 추측 공격에 충분하고, SMS 한 건 안에 들어간다.

```
https://smbe.net/w/   19바이트
<토큰 22자>           22바이트
안내 문구 (한글 10자)  20바이트
                     ─────────
                      61바이트   ← SMS 90바이트 한도 내
```

`/work-orders/<uuid>?token=<43자>` 형태였다면 무조건 LMS다. **짧은 경로 `/w/`는 요금 설계의 일부다.**

### 무효화 조건

`resolveAccessToken()`이 다음을 모두 확인한다. 하나라도 어긋나면 `null`이며, 어디서 걸렸는지는
밖으로 알리지 않는다.

| 조건                                      | 이유                             |
| ----------------------------------------- | -------------------------------- |
| `token_revoked_at IS NULL`                | 오발송·작업자 교체 시 즉시 차단  |
| `token_expires_at > now()`                | 무기한 유효한 링크를 남기지 않음 |
| `g.issue_version = w.issue_version`       | **재발급하면 옛 링크가 죽는다**  |
| 작업지시가 `ISSUED`/`IN_PROGRESS`, 미취소 | 끝났거나 취소된 작업에 접근 불가 |
| 작업자가 회사 활성 구성원                 | 퇴사·탈퇴 시 자동 차단           |

### 권한은 기존 서비스가 검사한다

`linkActor()`가 링크 권한을 기존 `Actor`로 변환하는 **유일한 통로**다. 변환 이후의 검사
(`memberAccess`, 회차 배정 확인, TBM 중복 방지 등)는 로그인 사용자와 완전히 동일하게 돈다.
링크라고 우회되는 경로를 만들지 않는다.

`WorkOrderLinkGrant`는 `companyId`/`userId`를 `worker` 아래에 감싸 둔다. 구조적 타이핑 때문에
평평하게 두면 `Actor`가 필요한 자리에 실수로 흘러들 수 있기 때문이다.

## 이 구조가 남기는 증빙의 수준

> **"해당 연락처로 보낸 링크가 열렸고, 확인이 눌렸다"**

그 이상이 아니다. 폰을 동료가 대신 눌렀는지는 알 수 없다.

이름을 입력받는 방식은 채택하지 않았다. 토큰이 이미 배정별이라 서버는 누구인지 알고 있고,
옆 사람도 이름은 아니까 입력을 받아도 본인 확인 강도가 올라가지 않는다. 대신 화면에 **이름을
표시**하고 확인만 받는다. 잘못 전달된 링크를 작업자가 스스로 걸러내는 효과도 있다.

**고객에게는 "전자적 확인 기록"이지 "본인 인증"이 아니라고 명확히 고지해야 한다.**
분쟁 시 이 구분이 중요하다.

강도를 올리고 싶으면 작업자가 한 번이라도 로그인해 계정을 연결하면 된다. 기본값은 무설치·무로그인,
계정 연결은 선택적 업그레이드로 둔다. 처음부터 강제하지 않는 것이 핵심이다.

## 열람 기록과 개인정보

`open_count`, `first_opened_at`, `last_opened_at`, `last_open_ip`, `last_open_agent`를 남긴다.
IP와 User-Agent는 개인정보이므로 **최신 1건만 덮어쓴다.** 이력 전체를 쌓지 않는다.

- 수집 목적: 작업지시 전달·확인 증빙
- 보존 기간: 작업지시 보존 정책을 따른다 (별도 확정 필요)
- 작업자 휴대폰번호 수집·이용 동의는 문자 발송 도입 시 함께 정리한다

## URL에 토큰이 남는 문제 — 해결됨

`/w/<토큰>` 은 페이지가 아니라 **Route Handler** 다 (`src/app/w/[token]/route.ts`).
토큰을 검증해 httpOnly 쿠키로 바꾸고 `/w` 로 리다이렉트하므로, 이후 주소창·히스토리에는
토큰이 남지 않는다. 쿠키 만료는 토큰 만료와 같다.

서버 컴포넌트 렌더 중에는 쿠키를 설정할 수 없어 Route Handler 여야 한다.

`next.config.ts`의 전역 `X-Robots-Tag: noindex`가 색인을 막고 있다. 공개 SEO 페이지를
예외 처리할 때 **`/w/*`는 반드시 noindex를 유지**해야 한다.

## 토큰은 보낼 때 만든다

`issueOrder` 가 아니라 `deliverOrder` 가 토큰을 발급한다. 평문은 발송 시점에만 존재하고
DB 에는 해시만 남기 때문이다(원문을 보관하면 해시로 저장하는 의미가 없다).

따라서 **링크를 다시 보내면 새 토큰이 나가고 이전 링크는 그 순간 무효가 된다.** 오발송·
기기 분실에 대응할 수 있으므로 제약이 아니라 성질로 둔다. 재발급 시 열람 기록도 초기화된다 —
그 링크의 열람 여부는 새 회차의 사실이기 때문이다.

## 제출 권한

`src/features/inspections/actions.ts` 의 `inspectionActor()` 가 로그인 사용자와 링크 방문자를
모두 받는다. 링크 방문자는 **토큰이 가리키는 작업지시 하나로만** 제한되고, 그 외에는 로그인
사용자와 완전히 같은 경로를 탄다. 회차 배정·TBM 중복·역할 검사는 `submitInspection()` 이
그대로 수행하므로 링크라고 우회되는 권한은 없다.

부적합 조치완료(`resolveFindingAction`)는 관리자 업무라 링크 방문자에게 열지 않았다.

## 사진 첨부 권한

`src/features/attachments/actions.ts` 도 같은 두 경로를 받는다. 사진 첨부 여부는 역할이
아니라 요금제가 가르는데, 사진을 찍는 사람은 현장 작업자이고 그 사람의 주 진입로가 링크다.
여기를 막으면 유료로 전환해도 정작 필요한 자리에서 기능이 닿지 않는다.

**역할은 첨부 권한을 가르지 않는다.** 유료 회사면 작업자도 표준서·평가를 포함해 어디든
올릴 수 있다. 가르는 것은 요금제 하나뿐이다.

링크에는 작업자와 작업지시가 들어 있으므로 서버가 **소속 회사를 따라가 요금제를 확인**한다.
그 위에 남는 제한은 **링크가 여는 범위**뿐이다.

| 검사 | 내용 |
| --- | --- |
| 대상 종류 | `work_order` · `inspection_result` · `inspection_finding` — `/w` 가 보여 주는 문서들 |
| 대상 소속 | 토큰이 가리키는 **그 작업지시**와 거기서 나온 점검 결과·부적합만 |
| 역할 | 회사에서 관리자인 사람이 링크로 들어와도 **작업자 권한으로만** 다룬다 |

세 번째 줄은 첨부 권한이 아니라 정리 권한에 대한 것이다. 토큰은 배정 하나를 여는 열쇠이지
관리자 자격을 옮겨 오는 물건이 아니므로, 링크 방문자는 본인이 올린 첨부만 확정·삭제한다.
첫 줄도 역할 제한이 아니다 — `/w` 화면이 보여 주는 문서가 늘면 목록도 는다.

사진은 점검을 **저장할 때 함께** 올라간다. 붙일 자리(`inspection_results` 행)가 저장 후에야
생기므로 화면이 파일을 들고 있다가 저장 직후 올린다. 업로드가 실패해도 점검 기록은 이미
저장된 상태라 날아가지 않는다.
