## 2026-09-22 가입할 때 연락처 받기 (알림 메일 · 휴대폰)

**받을 주소와 로그인 계정을 나눴다** (`0018`, `users.contact_email`).
`users.email` 은 소셜 로그인에서 따라온 값이고, 부분 유일 인덱스와 "다른
provider 로 같은 메일이면 병합하지 않고 비워 둔다" 는 규칙이 여기 매여 있다.
사람이 고칠 값이 아니다. 그런데 현장에서 지시서·승인요청·회의 알림을 받고
싶은 주소는 카카오에 딸려온 개인 주소가 아니라 회사 메일인 경우가 많다.
그래서 **받을 주소**를 따로 두고, 보내는 자리는 전부
`COALESCE(contact_email, email)` 로 바꿨다 — 따로 정하지 않은 사람은 예전과
똑같이 받는다. 로그인은 `user_identities` 로 하므로 주소를 바꿔도 로그인은
그대로다.

**가입하는 세 갈래 모두에서 받는다.** 회사 만들기 · 회사코드 참여 · 초대 수락은

- 메일은 **로그인에 연동된 주소가 기본값**이고 바꿀 수 있다.

**한 번 넣고 못 고치면 안 되므로 마이페이지에도 넣었다.** [내 정보] 에 '알림

## 2026-09-22 화면 다듬기 — 단계 띠 · 메뉴 접기 · 하단 고정 저장

**작업지시의 탭을 단계 띠로 바꿨다.** 나란한 네모 버튼은 "골라 보는 것"으로
보이는데, 작업 정보 → 위험성평가 → 일정·인원 → 체크리스트 → QR 은 실제로
그 순서로 일어나는 일이다. 번호를 원으로 두고 선으로 이어, **지나온 구간에만
선에 색이 차게** 했다. 지금 어디인지가 번호를 세지 않아도 보인다.

작성 화면의 단계(`.wo-steps`, 버튼)와 발급 후 열람 탭(`.wo-doc-tabs`, 링크)은
같은 순서를 걷는 같은 화면이라 모양을 하나로 합쳤다. 열람 쪽만 링크인 것은
URL 에 남기기 위해서다. 번호는 `aria-hidden` 이라 링크 이름은 "위험성평가"
하나다 — "2 위험성평가" 로 읽히던 것을 고쳤다.

**마이페이지의 칸을 줄였다.** 소속·역할과 내 정보·연락처는 따로 볼 일이 없다
("나는 이 회사의 무엇이고 연락은 이리로 온다"는 한 덩어리다). 한 칸으로 합치고,
"소속 상태" 는 역할 뒤에 붙였다(재직 중이면 굳이 적지 않는다). 칸이 셋이 되어
마지막 하나가 반쪽으로 남으므로 소속 이력은 아래 줄을 통째로 쓴다.

**메뉴의 안전점검·회사정보는 접어 둔다.** 다 펴 두면 목록이 길어져 정작 자주
쓰는 작업지시·표준서가 좁은 화면에서 스크롤 밖으로 밀렸다. 지금 보고 있는
화면이 그 안에 있으면 처음부터 펴 둔다 — 내가 어디 있는지가 접혀 있으면 안 된다.

> `display` 를 직접 정한 요소에는 브라우저 기본 `[hidden] { display: none }` 이
> 밀린다. `.nav-group-children` 이 `display: grid` 라 처음엔 접어도 그대로
> 보였고, 테스트가 이걸 잡았다.

**표준서가 없을 때 [표준서 만들기] 가 두 개였다.** 화면 머리에 하나, 빈 목록
안에 또 하나. 작업지시 목록은 머리의 버튼 하나만 두므로 그쪽에 맞췄다.

**하단 고정 저장 줄을 긴 폼 공통으로 폈다** (`.sticky-actions`). 작업지시
작성에서 쓰던 것을 표준서 작성·수정, 위험성평가 회차, PTW 신청, 주간회의에도
건다. 위쪽을 고치다 저장하려고 몇 화면을 다시 내려가야 하던 것이 없어진다.
폼이 짧으면 `sticky` 는 제자리에 그려지므로 아무 일도 일어나지 않는다.

- 재검증: `npm run typecheck`·`lint`·`build`, `test:db` (44), `test:attachments`
  (12), `npm run test:orders-ui` (17 passed / 1 skipped). 테스트에 세 가지를
  더했다 — 메뉴 그룹이 접힌 채로 열리는지, 그 안의 화면에 들어가면 펴져
  있는지, `/standards/new` 의 저장 줄이 좁은 화면에서 화면 안에 붙어 있는지.

## 2026-09-22 앱 틀 — 본문만 스크롤, 상단바 한 줄, 같은 색

"메인이 스크롤되면 웹페이지 같다"는 지적에서 시작했다. 원인은 세 가지가 겹쳐
있었다 — 문서 전체가 스크롤돼 주소창이 접히고 튕기는 것, 검은 공지 띠·흰 상단바·
회색 본문으로 위쪽 색이 세 층인 것, 제목이 상단바와 본문 머리말에 두 번 나오는 것.

- **앱 틀 (≤960px).** `body:has(.app-shell)` 를 화면 높이로 고정하고 본문(`main`)만
  세로 스크롤 영역으로 만들었다. 상단바는 그 밖에 고정이라 주소창이 접히지 않고
  튕김도 본문 안에서만 난다. 화면이 바뀌면 본문을 맨 위로 올린다(app-shell.tsx).
  본문이 밑으로 들어가면 상단바에 그림자만 켠다(`.is-scrolled`). 공지 띠는 이
  틀에서 접는다. 고정 머리(단계 탭·구간 탭)의 top 은 0 이 됐다.
- **한 면의 색.** 상단바 배경을 본문과 같은 회색으로, 실선은 없앴다. 매니페스트와
  viewport 의 테마 색도 배경색으로 바꿔 상태 표시줄까지 한 면이다.
- **제목 한 줄.** 상단바의 `h1` 하나만 남기고 본문 머리말의 제목·뒤로가기는
  숨긴다. 왼쪽 자리는 메뉴 주소 그 자체면 ☰, 그 아래 주소면 ← (`navRoot`,
  sidebar.tsx). 뒤로 갈 곳은 그 메뉴 주소다. 어느 메뉴에도 없는 화면(마이페이지)은
  첫 화면으로 쳐서 ☰ 을 유지한다. 상단바 제목은 이동 경로의 마지막 조각이라,
  본문 제목과 달랐던 화면(지시서 상세·점검·회의·장소·판단 기준)의 쉘 제목을 맞췄다.
- **홈 한 화면.** 타일 네 개를 한 줄에, 시작 카드 두 장은 아이콘 붙은 버튼 한
  줄로. 나머지 공간을 목록이 채우며 스크롤된다.
- **막힌 것.** 옆으로 미는 탭 띠의 내용 너비(419px)가 문서의 최소 너비로 번져
  모바일 브라우저가 화면을 그 너비로 넓혀(축소해) 버렸다 — 문서 스크롤일 때는 안
  나던 일이다. 띠에 `contain: inline-size`, 본문 자식에 `min-width: 0`. 띠의
  현재 탭 끌어오기는 `scrollIntoView` 가 조상(본문·문서)까지 밀어 버려 띠 자신만
  `scrollTo` 한다.
- 검증: 브라우저 e2e 전체(데스크톱·모바일) 통과. 진단용 스펙으로 뷰포트·문서
  높이가 화면과 같음을 확인했다(문서 높이 844 = 화면 높이).

## 2026-09-22 작업자 홈 — 오늘 작업 카드

작업자가 로그인해서 보는 홈은 관리자 홈에서 관리자 타일만 뺀 모양이었다. "오늘
작업 0건" 타일, "내 작업 확인하기" 카드, 예정·진행 작업 전체 목록. 작업자가 홈에서
할 일은 오늘 회차의 TBM 하나다.

- 오늘 회차가 있는 배정 작업마다 큰 카드 하나. 작업명·시간·장소와 카드 안의
  [TBM 확인]·[작업 중 점검]. 상세 화면을 거치지 않고 점검 폼으로 바로 간다.
  TBM 을 찍었으면 버튼 대신 '확인 완료'.
- 오늘 회차가 없으면 한 줄 안내와 다음 작업일. 내 TBM 이 빠진 지난 회차가 있으면
  '지난 회차 미입력 n건' 링크 하나. 미래 작업은 '다른 작업 보기' 뒤로.
- 회차 판정은 점검 화면과 같은 `sessionState` 를 쓴다(야간조 자정 넘김 포함).
  배정 작업 30건까지 회차를 훑는다 — 작업자 한 명에게 그 이상 배정되는 일은 없다.
- 관리자 홈은 그대로다. `Dashboard` 가 `worker` 데이터를 받으면 작업자 화면으로
  갈라진다. e2e(inspections.spec)가 TBM 전·후의 카드 상태를 확인한다.

## 2026-09-22 모바일 사용성 일괄 손질

하단 탭 바를 뺀 나머지 추천안을 한 번에 넣었다. 기준은 하나 — 현장에서 한 손으로,
장갑 낀 손가락으로도 되는가.

- **확인 창.** 브라우저 `confirm()` 은 긴 문장을 좁은 창에 줄글로 띄우고 버튼도
  못 바꾼다. `useConfirm()`(components/ui/confirm-dialog.tsx) 로 바꿨다. 좁은
  화면에서는 아래에서 올라오는 시트, 넓은 화면에서는 가운데 카드. 발급·취소·
  삭제·폐기·퇴사·사진 삭제가 이걸 쓴다. 폼 제출 확인은 제출을 한 번 막았다가
  확인되면 `requestSubmit()` 으로 다시 낸다 (ref 로 되돌이 방지).
- **점검 폼.** '전부 적합으로 표시' 한 번 누르고 예외만 바꾼다. 저장 버튼은
  아래에 붙고, 저장 전에 적합·부적합·해당없음 수를 보여 준 뒤 저장한다 — 저장
  후 수정이 안 되기 때문이다.
- **상단 공간.** 공지 띠는 닫을 수 있고 좁은 화면에서 36px. 닫힘은
  `html[data-banner-hidden]` 으로 `--banner-h` 를 0 으로 만든다(상단바·고정 머리가
  이 값을 본다). 첫 그리기 전에 적용하려고 layout 에 인라인 스크립트. 로그아웃은

## 2026-09-22 초안 삭제 · 이동 중 표시

**지우는 자리는 목록이다.** 처음에 상세 화면 아래에 제목과 설명이 달린 절을
하나 만들었는데, 잘못 만든 초안이 여러 개 쌓였을 때 하나씩 상세로 들어갔다
나오라는 소리였다. 삭제는 버튼 하나면 되는 동작이고, 그 버튼이 있어야 할 곳은
목록의 그 줄이다. 상세에는 액션 줄(목록·편집·복사 옆)에 같은 버튼을 둔다.
목록에서 지우면 그 줄만 사라지면 되므로 이동하지 않고, 상세에서 지우면 그
자리가 404 가 되니 목록으로 보낸다.

**지시서 삭제는 초안에만 연다.** 발급된 지시서는 법정 기록이고 회차·점검·
부적합이 딸려 있어, 지우면 증빙에 구멍이 난다 — 그 경우의 수단은 이미 있는
'취소'다. 지울 수 있는 것은 아무도 본 적 없는 초안뿐이고, 목적은 잘못 만든
초안이 목록에 영원히 쌓이지 않게 하는 것이다. 화면에서도 초안에는 [초안 삭제]
가, 발급 뒤에는 [지시서 취소]가 나오며 둘이 동시에 보이지 않는다.

**행은 지우지 않고 감춘다** (`0017`, `deleted_at`·`deleted_by`). 초안에도 간이
평가·배정이 딸려 있어 물리 삭제하면 정리할 것이 줄줄이 나오고, 실수로 지운 것을
되돌릴 방법이 없어진다. 발급된 지시서에 삭제 표시가 서지 않도록 **CHECK 로도**
막았다 — 앱이 실수해도 DB 가 거절한다. 테스트가 그 제약 이름까지 확인한다.

**이동 중에 아무 표시가 없던 것도 고쳤다.** App Router 는 서버 컴포넌트를 받아
와야 화면을 바꾸므로, 링크를 누르고 응답이 올 때까지 정말 아무 일도 일어나지
않는다. 루트 `loading.tsx` 가 있어도 소용이 없다 — 그 경계는 이미 마운트돼
있고, 새로 진입하는 세그먼트(`/work-orders/new` 등)에는 `loading.tsx` 가 없다.

화면 전체를 덮는 대신 **누른 그 버튼 안에서** 스피너를 돌린다(`useLinkStatus`).
어디를 눌렀는지는 사용자가 이미 아니까, 그 자리에서 도는 편이 덜 거슬린다.
링크는 도는 동안 흐려지고 눌리지 않아 중복 클릭도 막힌다. 뒤로가기는 링크가
아니라 `router.back()` 이므로 `useTransition` 으로 같은 표시를 한다.

- 붙인 곳: 작업 지시하기, 상태 탭, 페이지 이동, 목록·편집·복사, 지시서 상세 탭,
  TBM/작업 중 점검 버튼, 뒤로가기.
- **목록의 줄 자체**가 빠져 있었다. 정작 가장 많이 누르는 곳이라, 링크에 스피너를
  미리 물린 `NavLink` 로 묶어 목록 화면 전체에 적용했다 — 작업지시 목록의 카드·행,
  점검 기록의 회차, 모니터링의 작업명과 점검 보기, 주간 회의 목록, 홈의 작업 카드,
  작업자 화면(`/w`)의 회차 버튼. 링크가 여러 개인 화면에서 하나씩 손으로 넣다가
  빠뜨리는 것을 막으려고 컴포넌트로 만들었다.
- 검증: lint·typecheck·build, DB 44(초안 삭제 1건 신규 — 권한·낙관적 잠금·
  조회 제외·재삭제·발급본 거절·DB 제약), 브라우저 17(초안/발급 상태에 따라
  삭제·취소가 갈리는지). **마이그레이션 `0017` 적용 필요.**

## 2026-09-22 점검 모니터링 (I-04)

안전점검 파트의 마지막 화면. 설계에 기능명만 있던 것을 현재 데이터로 구성했다.

하나를 고르고, 회차가 아니라 "그 날 도는 작업"을 행으로 놓는다. 미이행 작업은

추이 그래프도 재해율 통계도 넣지 않았다. 첫 화면이 답해야 하는 질문은 "누가 아직

누구를 불러야 할지 모른다.

**미조치 부적합만 전체 기간을 센다.** 조치는 작업일과 무관하게 남으므로 날짜로

것을 테스트로 고정했다.

"무료 홈·지시서의 상태 확인을 이 메뉴로 옮겨 유료화하지 않는다" 고 적혀 있고,

## 2026-09-22 미실시 주 회의 메일 알림 — 관리감독자·안전관리자

빠진 주는 화면에 표시되지만 화면을 열어야 보이고, **열지 않는 회사가 정확히

받는 사람은 관리감독자와 안전관리자다. 그 주의 회의를 실시할 책임이 있는
역할이고, 작업자에게 보내면 자기가 할 수 없는 일을 통보받는 셈이 된다.
요금제로는 가르지 않는다 — 안전 알림을 유료 기능으로 두면 중대재해 맥락에서

**앱 안에 스케줄러를 두지 않았다.** 컨테이너가 여러 개로 늘어나면 각자 타이머를

`POST /api/cron/meeting-reminders` 를 때리고(`CRON_SECRET` 인증, readiness API와
같은 timing-safe 비교), 중복 방지는 DB 가 맡는다.

`0016` 으로 발송 장부를 따로 뒀다. 회의가 없는 주에는 `safety_meetings` 행 자체가
없어 "알렸다" 를 적을 자리가 없다. 그 주를 DRAFT 로 만들어 두는 방법도 있지만,
아무도 열지 않은 회의를 "작성 중" 으로 세우면 목록이 거짓말을 한다.
`(company_id, week_start)` 유일 제약이 같은 주를 두 번 알리지 않게 막는다.

- 회의 목록은 미실시 주에 "미실시 알림 발송 <날짜>" 를 함께 보여준다. 알림이

- **설치를 스크립트로 만들었다.** 처음에 "`.env` 에 CRON_SECRET 넣고 cron

  시크릿 생성·컨테이너 재생성·crontab 등록·시험 실행까지 하고 결과를 설명한다.

  도착 시간만 정한다 — 서버 시간대를 계산할 필요가 없고 하루 놓쳐도 따라잡는다.

  확인·증상별 문제 해결 순서. docker.md 는 명령어 사전으로 남기고 여기로 링크한다.

## 2026-09-22 주간 안전점검 회의 (I-03)

상시평가의 "매주 논의·공유·이행점검" 요건을 담는 메뉴다. 법적으로 이 제품의
명분에 가장 가까운 화면이고, `0014` 의 세 테이블이 드디어 쓰인다.

**회의의 역할은 처리가 아니라 확인이다.** 회의에서 항목을 체크해도 원본 부적합
이나 평가 대책은 종결되지 않는다. 종결은 각 처리 화면의 몫이고, 여기서는 그
주에 무엇을 논의했는지가 남는다. 그래서 수집 항목은 원본에 FK 를 걸지 않고
수집 시점 사본(`summary`)을 들고 있다 — 원본이 나중에 바뀌어도 그 주의 기록은
그대로다.

**주는 한국시간 월요일 시작.** 회차(작업일자)와 같은 시간대를 쓰지 않으면
금요일 야간작업의 부적합이 다음 주 회의로 밀린다. 월요일이 아닌 날짜와 아직
오지 않은 주는 거부한다.

**수집을 여러 번 한다.** 작성 중인 회의는 [다시 수집]으로 주 중간에 생긴 항목을
덧붙일 수 있고, 이미 적은 확인·비고는 `UNIQUE(meeting_id, source_type,
source_id)` 덕에 보존된다. 완료된 회의에는 더 붙이지 않는다 — 회의가 끝난 뒤
생긴 건은 다음 주의 몫이다.

수집 대상은 그 주의 점검 부적합(조치대기·조치완료 모두)과, 기한이 그 주까지인데
완료되지 않은 **승인된** 평가의 감소대책이다. 작성 중인 평가의 대책은 아직 이행
의무가 아니라 제외했다. 안전사고는 테이블 자체가 없어 `source_type` 에 자리만
두고 비워 뒀다.

**완료 조건은 참석자 1명 이상뿐이다.** 논의 내용은 비워도 된다. 확인 위주로 수
분 내에 끝나야 매주 돌아가고, 필수 서술을 강요하면 형식적인 한 줄만 남는다.
미확인 항목이 있어도 막지 않고 몇 건인지 보여준다. 완료하면 잠기고 다음 주
회의에서 이어 다룬다.

- 목록은 **주를 먼저 세우고** 회의를 붙인다. 회의 행만 나열하면 미실시 주가
  목록에서 사라져, 정작 봐야 할 "빠진 주"가 안 보인다.
- 사이드바의 안전점검을 그룹으로 바꿔 점검 기록과 나란히 뒀다 (설계의 "안전점검
  메뉴 하위").
- 월별 발굴·조치 집계는 목록 위 한 줄로 얹었다. 신규 월간 메뉴는 만들지 않는다.
- 미실시 주 메일 알림은 미구현이다 — 스케줄러가 없다.
- 검증: lint·typecheck·build, DB 41(회의 1건 신규 · 수집·재수집·완료 잠금·권한),
  첨부 12, 브라우저 17(회의 열기 → 완료 → 목록 반영). 마이그레이션 변경 없음.

## 2026-09-22 점검 기록 화면 (I-01) · 관리자 사후 입력 · 수정 이력

`0014` 로 테이블만 만들어 두고 쓰는 화면이 없던 것을 채운다. 스키마만 있고
안 쓰는 상태가 제일 나쁘다.

**회사 전체 점검 기록.** 지금까지 점검 기록은 작업지시를 하나씩 열어야 보였다.
"지난달 우리 회사 TBM 기록" 에 답할 수 없었고 그게 감사 대응의 본체다.
`/inspections` 에 기간·작업명·상태 필터가 붙은 회차 목록을 놓았다. **회차가
행인 이유는 이 화면의 목적이 누락을 찾는 것**이기 때문이고, 점검 구분·결과별
상세는 회차를 열어서 본다. 목록에서 회차를 누르면 그 회차가 열린 기존 상세
화면으로 간다 — 기록 렌더링을 두 번 만들지 않는다.

상태 필터(누락만·완료만·미조치 부적합·사후 입력 포함)는 집계 결과에 걸리는
조건이라 SQL 뒤에서 걸렀다. 무료는 최근 1주일만 보이고 그 이전은 건수만 남는다.

**관리자 사후 입력.** 현장에서 못 찍고 지나간 회차를 대신 채우는 길이다.
기록이 비어 있는 것보다 "누가 언제 대신 넣었는지 드러난 기록" 이 감사에 낫다는
판단이고, 그래서 현장 입력으로 위장되지 않는 것이 이 기능의 전부다 —
`inspector_id` 와 `recorded_by` 가 갈라지고, `backfilled` 가 서고, 경로는 WEB
으로 못박히며, `submitted_at` 은 지금 시각 그대로다. 기록 목록에서는 펼치지
않아도 "사후 입력" 표식이 보인다. 훑는 사람이 현장 입력과 구분하지 못하면
표시한 의미가 없다.

배정되지 않은 작업자의 기록은 만들어 낼 수 없다. 관리자는 순회점검으로 참여할
수 있으므로 배정과 무관하게 허용한다 — 현장 입력과 같은 규칙이다. 같은 회차의
TBM 은 현장 입력이든 대리 입력이든 한 번뿐이다.

**결과 수정 + 이력.** 수정할 수 없는 기록은 틀린 채로 남고, 흔적 없이 고칠 수
있는 기록은 증빙이 아니다. 그래서 사유를 받고 수정 전·후를 통째로
`inspection_revisions` 에 남긴다. 부적합은 결과를 따라가되 **이미 조치완료된
건은 되돌리기를 거부한다** — 조치 내용과 담당자 기록까지 지우는 일이라 수정이
아니라 삭제다.

- `submitInspection` 은 손대지 않고 검증 조각(체크리스트 완전성·부적합 담당자)만
  떼어내 세 경로가 같은 규칙을 쓴다. 동시성이 걸린 함수를 다시 짜지 않았다.
- 검증: lint·typecheck·build, DB 40(사후 입력·수정·목록 3건 신규), 첨부 12,
  브라우저 17(목록 필터와 사후 입력 표식을 새로 검증). 마이그레이션 변경 없음.

## 2026-09-22 지시서 출력물 — 현장 게시용 A4 한 장, 유료 전환

인쇄물의 목적을 다시 잡았다. 화면의 지시서 상세는 법정 기록 전체를 담고,
인쇄물은 **작업 장소에 붙여 두는 게시물**이다. 목적이 다르니 같은 것을 인쇄할
이유가 없다. 문서 전체를 여러 장으로 뽑는 대신, 한 장에 들어갈 것만 골라
담는 전용 레이아웃(`print-sheet.tsx`)을 만들었다 — 작업명·기간·장소·PTW·배정
인원·위험요인과 감소대책·TBM/작업 중 체크리스트, 그리고 QR.

`@page { size: A4 }` 에 맞춘 조판이고, 화면에서는 아예 보이지 않으며 인쇄에서만
나온다. 반대로 화면 문서(`.wo-print`)는 인쇄에서 통째로 빠진다. 어느 탭을 보고
있든 같은 한 장이 나간다.

**설계 되돌림 — 출력물을 유료로 옮겼다.** v2.6 에서 "지시서 출력물은 무료
허용" 으로 정했던 것을 뒤집는다. 무료 회사는 버튼을 눌렀을 때 안내로 막는다.
버튼을 숨기지 않은 이유는, 없으면 "이 제품에는 출력이 없다" 로 읽히지만 안내가
뜨면 무엇을 얻는지 알고 결정할 수 있기 때문이다.

이 전환의 대가는 분명하다. `notifications.md` 의 채널 매트릭스에서 무료는
"메일 + QR(대면 배포)" 였는데, 그 QR 이 인쇄물이었다. 이제 무료의 대면 배포는
**화면의 QR 을 보여 주는 것**으로 좁아진다. 메일 링크는 그대로다. 관련 문서
(설계 v5.8, 채널 매트릭스, 메뉴 레이아웃 W-03·W-05)를 모두 맞췄다.

- 항목이 아주 많은 지시서는 두 장이 될 수 있다. 각 블록이 페이지 중간에서
  잘리지 않게만 막았고, 내용을 조용히 잘라내지는 않는다 — 법정 기록에서 잘린
  줄은 없는 줄이 된다.
- 검증: lint·typecheck·build, 브라우저 17 통과(무료 차단 안내와 유료 출력물을
  각각 검증). 마이그레이션 변경 없음.

## 2026-09-22 지시서 상세를 작성 단계와 같은 탭으로

발급된 지시서 상세는 한 장짜리 긴 문서였다. 모바일에서 11,000px 이 넘었고,
발급 직후 정작 할 일(QR 뽑아 붙이기·링크 전달)이 그 맨 아래에 있었다.

작성 폼의 1~4 단계를 열람에도 그대로 쓰고, 발급되면 **5번 QR·전달 탭**이
생긴다. 같은 번호를 쓰는 이유는 "3번에 뭘 넣었더라"를 같은 자리에서 찾게
하려는 것이다. 발급 직후에는 5번 탭으로 바로 보낸다.

- **인쇄는 탭과 무관하게 전체가 나간다.** 지시서는 법정 서류라 탭 단위로 쪼개
  인쇄되면 안 된다. 접힌 탭도 DOM 에 남기고 `@media print` 에서 `[hidden]` 을
  풀어, 어느 탭을 보고 있든 한 장으로 출력된다. 인쇄 창에서 대상을 'PDF로
  저장'으로 바꾸면 PDF 가 된다. 브라우저 테스트가 이 규칙을 지킨다.
- **탭은 URL(`?tab=`)에 있다.** 클라이언트 state 로만 잡으면 새로고침·뒤로가기·
  링크 공유가 전부 깨진다. 서버 컴포넌트가 그대로 렌더하고 탭은 링크다.
- **작업자에게는 탭을 쓰지 않는다.** 작업자에게 필요한 건 다섯 개의 탭이 아니라
  [TBM 확인하기] [작업 중 점검하기] 두 개다. 한 장으로 펼친다.
- 상태 4칸·회차 요약·취소·변경 이력은 탭 밖에 뒀다. 어느 탭에 있든 보여야
  판단이 되고, 취소는 탭 안에 숨기면 오히려 위험하다.
- `orderCommandAction` 의 redirect 는 try 밖에서 던진다. Next 의 redirect 는
  예외로 동작해서 try 안에 두면 catch 가 "처리하지 못했습니다" 로 삼킨다.
- 검증: lint·typecheck·build, 브라우저 17 통과(발급 후 탭 이동·인쇄 시 전체
  노출을 새로 검증). 마이그레이션 변경 없음.

## 2026-09-21 점검 사진 — 역할 제한 제거, 항목별 첨부, /w 버튼

앞선 라운드에서 첨부 권한 경로만 열어 두고 화면을 안 만들었는데, 정책 자체가 내
이해와 달랐다. 세 가지를 바로잡았다.

- **역할은 첨부 권한을 가르지 않는다.** 그동안 `WORKER_TARGETS` 로 작업자를
  작업지시·부적합에만 묶어 뒀다. 표준서도 작업자가 입력할 수 있는 문서이므로 이
  제한을 통째로 걷어냈다. 이제 가르는 것은 **요금제 하나뿐**이다.
- **사진은 항목마다 붙는다.** 지금까지 점검 쪽 첨부 대상은 부적합(`inspection_finding`)
  하나였다. 그런데 현장에서 찍는 사진은 부적합 증거만이 아니다 — "가드가 닫혀 있다"
  같은 적합 판정의 근거도 사진이 가장 빠른데 붙일 자리가 없었다. `0015` 로
  `inspection_result` 를 첨부 대상에 추가했다. 항목당 한 행이라 결과에 관계없이
  사진의 집이 된다.
- **`/w` 와 웹 점검 화면 양쪽에 사진 버튼을 달았다.** 유료 회사면 링크로 들어온
  작업자도 무조건 올릴 수 있다.

붙일 자리가 저장 후에야 생기는 것이 이 구현의 본체다. 그래서 저장 흐름을 바꿨다.
`submitInspectionAction` 이 서버에서 바로 redirect 하지 않고 **항목별 결과 행 id 와
다음 화면**을 돌려주고, 화면이 들고 있던 파일을 그 자리에 올린 뒤 이동한다. 업로드가
실패해도 점검 기록은 이미 커밋됐으므로 기록이 날아가지 않고, 실패만 알린다.

압축·presign·confirm 경로는 `attachments/upload.ts` 로 떼어내 표준서(즉시 업로드)와
점검(저장 후 일괄 업로드)이 같은 코드를 쓴다.

남은 제한은 역할이 아니라 **링크가 여는 범위**다. 토큰 방문자는 그 작업지시와 거기서
나온 결과·부적합에만 붙일 수 있다. 토큰은 배정 하나를 여는 열쇠이지 관리자 자격을
옮겨 오지 않으므로, 회사에서 관리자인 사람이 링크로 들어와도 본인이 올린 첨부만
정리할 수 있다. `/w` 가 보여 주는 문서가 늘면 이 목록도 늘린다.

- 검증: lint·typecheck·build, DB 37, 첨부 12, 브라우저 17 통과. 마이그레이션 `0015` 적용 필요.

## 2026-09-21 안전점검 파트 착수 전 설계 정합성 정리

TBM·안전점검을 본격적으로 만들기 전에, 그동안 바꾼 설계가 문서와 코드에 어디까지
반영됐는지 맞췄다. 여덟 군데가 어긋나 있었다.

- **작업자 진입 경로가 두 개인데 문서는 하나만 알고 있었다.** 설계 문서 §10 은 아직 "QR 스캔
  → 로그인 → 점검"과 "로그인 계정이 TBM 증빙"이라고 적혀 있었다. QR은 **그대로 두기로 확정**
  했다 — 종이에 찍혀 돌아다니는 코드에 개인 열쇠를 넣지 않는다. QR은 "이 지시서"까지만
  가리키고 "누가 열었는가"는 로그인이 답한다. 개인화는 토큰 링크가 담당한다. 증빙 수준은
  경로별로 다르게 적었다 (로그인은 계정, 링크는 "그 연락처로 보낸 링크가 열리고 확인이
  눌렸다"는 사실).
- **링크 방문자가 사진을 못 올리고 있었다.** "첨부는 역할이 아니라 요금제가 가른다"고 정해
  놓고도 첨부 액션은 로그인 세션만 받았다. 사진을 찍는 사람은 현장 작업자이고 그 사람의
  주 진입로가 링크라, 유료로 전환해도 정작 필요한 자리에서 기능이 닿지 않았다. 링크에는
  작업자와 작업지시가 들어 있으니 소속 회사를 따라가 요금제를 확인할 수 있다.
  범위는 두 겹으로 좁혔다 — 토큰이 가리키는 작업지시(와 거기서 나온 부적합)에만, 그리고
  회사에서 관리자인 사람이 링크로 들어와도 작업자 권한으로만. **토큰은 배정 하나를 여는
  열쇠이지 관리자 자격을 옮겨 오지 않는다.**
- **"Pro"가 두 뜻이 돼 있었다.** 기능을 가르는 무료/유료 경계이기도 했고 ~99인 구간의
  이름이기도 했다. "Pro 요금제에서 사진을 첨부할 수 있습니다"를 Basic 고객이 읽으면 자기는
  못 쓰는 기능이 되는데 실제로는 된다. 화면 문구를 전부 "유료"로 바꾸고 구간 이름은 요금제
  화면에만 남겼다. 서버 게이트(`pro_state !== 'FREE'`)는 한 줄도 건드리지 않았다.
  덤으로, 사이드바 요금제 표시는 아무도 값을 넘기지 않아 유료 회사에도 "무료티어"라고
  적혀 있었다. 세션이 `pro_state` 를 들고 오게 하고 셸마다 실제 값을 넘긴다.
- **작업표준서 ≠ 위험성평가**를 설계 문서에도 반영했다. 코드는 이미 지시서에 굳은 평가
  스냅샷을 읽고 있었고 문서만 "표준서 위험요인 표시"로 남아 있었다.
- **판단 기준을 TBM 화면에 접어서 넣었다.** 위험요인마다 위험성 수준과 허용 가능 여부를
  붙이고, 그 수준을 무엇으로 갈랐는지는 버튼을 눌러야 펼쳐진다. 기준 원문이 길어 펼쳐
  두면 체크리스트가 밀리고 매번 읽을 내용도 아니다. 보여 주는 값도 평가 사본 안의 기준이라
  회사가 기준을 바꿔도 이미 나간 지시서의 현장 화면은 그대로다.
- **PTW 승인 상태를 작업자 화면에 표시**한다. 설계대로 점검을 막지는 않는다. 막는 대신
  허가가 안 난 상태라는 걸 현장이 알고 있게 하는 것이 목적이다.
- **`0014` 로 안전점검 테이블을 세팅했다.** 사후 입력(`recorded_by`·`backfilled`), 수정 이력
  (`inspection_revisions`), 주간 안전점검 회의(`safety_meetings` 3종).
  `inspector_id` 는 누구의 점검인가이고 `recorded_by` 는 누가 실제로 타이핑했는가다.
  `submitted_at` 은 언제나 실제 저장 시각이라 사후 입력을 과거 현장 입력으로 보이게 만들
  수 없고, 같은 이유로 사후 입력은 웹에서만 가능하도록 CHECK 로 못박았다.
  회의 수집 항목은 원본에 FK 를 걸지 않는다 — 부적합·사고·감소대책이 서로 다른 테이블이고
  안전사고는 아직 테이블이 없다. `summary` 가 수집 시점 사본이라 원본이 바뀌어도 그 주에
  무엇을 논의했는지가 남는다. 회의에서 확인해도 원본 부적합은 종결되지 않는다.
- **문서끼리 어긋난 곳**도 정리했다. `notifications.md` 가 열람 집계를 `work_order_outputs`
  라고 적고 있었지만 `0011` 에서 `work_order_access_grants` 로 옮겼고, 구현 순서의 3~5번은
  이미 끝난 일이었다. 설계 문서의 요금제 절은 두 세대 전 모델(인원 한도 + 인당 1만원 +
  일할 계산)이 그대로 남아 있어 현재 구간 정액제로 갈아엎었다. 메뉴 레이아웃에는 로그인
  전제 화면(M-01·M-02)만 있고 무로그인 링크 방문자 동선이 없어 `M-00` 으로 추가했다.
- 남은 것: 점검 폼의 사진 첨부 UI, I-01 점검 기록 화면, 사후입력·수정 UI, 주간 회의 화면,
  점검 모니터링. 마이그레이션 `0012`·`0013`·`0014` 운영 적용 필요.
- 검증: lint·typecheck·build, DB 37(사후입력 신규), 첨부 12(링크 범위 4건 신규),
  브라우저 17 통과.

## 2026-09-21 점검 회차 판정 단순화 — 작업일자만 기준

- 지금까지 회차 입력 가능 판정은 "시작 2시간 전 ~ 종료 2시간 후" 시간대 창이었다. 도입기 사용자에게 이 창은 너무 촘촘했다. 회차 시간을 놓치면 TBM을 아예 못 찍는 상황이 반복돼 정착이 어려웠다. 게이트를 **작업일자(KST) 하나**로 재정의한다.
- 상태 값도 다시 짰다. `DONE/OPEN/SCHEDULED/MISSED` 4단계 대신 `FUTURE/TODAY/PAST` 3단계 + `done` 불리언. 상태는 라벨이고 게이트는 `canInput = state !== "FUTURE"` 하나. 오늘·지난 회차는 QR/링크/웹 어디로 들어와도 입력 가능하다.
- **감사 증빙은 실제 저장 시각(`submitted_at`)이 대신한다.** 지연 입력 배지는 넣지 않았다 — 처음엔 남길지 물었으나 사용자가 "단순함 우선"으로 결정. `submitted_at`이 회차 종료 시각과 얼마나 벌어졌는지는 필요할 때 조회에서 계산할 수 있다.
- 미래 회차는 목록에 표시하되 액션 버튼을 숨긴다. 아직 시작 안 한 회차의 TBM을 미리 찍는 건 의미가 없기 때문. 목록에서만 보여 전체 일정을 공유하는 효과는 유지.
- 오늘 회차가 없는 상태(예: 첫 작업일이 아직 시작 안 함, 또는 모든 회차 지남)에도 화면이 죽지 않는다. `data.current`가 null이면 요약 패널은 안내 문구를 노출하고 목록에서 지난 회차를 이어 입력하도록 유도한다.
- 서버 게이트도 함께 완화: `submitInspection`에서 `!sessionState(session, now).open` → `!sessionState(session, now).canInput`. 이제 미래 회차만 거절하며 에러 문구도 "아직 시작하지 않은 회차입니다"로 명확해졌다. `readOrder`의 `currentSession`, `inspectionOverview`의 `current` 모두 `state === "TODAY"`로 다시 정의.
- 이전 회차 부적합 조치 팝업은 **오늘 회차에서만** 노출한다. 지난 회차를 뒤늦게 입력할 때 팝업이 뜨면 흐름이 어지러워지고 문맥이 다르다. `target.id === data.current?.id`일 때만 `previousActions`를 폼에 넘긴다.
- UI:
  - `/w` — 헤더 아래 회차 목록. 오늘은 강조, 지난은 클릭 가능, 미래는 목록에만 노출. 각 카드에 TBM/작업 중 버튼. `?session=<id>&type=TBM|DURING_WORK`로 진입해 폼을 편다.
  - `/work-orders/[id]/inspections` — 기존 요약 패널 유지(오늘 회차 요약), `?session=<id>` 파라미터로 지난 회차 진입 가능. 회차 목록의 각 `<details>` 안에 액션 버튼 추가.
  - 회차 정렬은 `orderSessionsForDisplay` 헬퍼로 두 화면이 동일 규칙: 오늘 → 지난(최근순) → 미래(가까운 순). SQL 은 그대로 `work_date DESC` 로 두고 표시만 다시 정렬한다.
  - `.link-session-list` CSS 신설: 카드형 리스트, 상태별 배지 색상 분기.
- 설계 문서 갱신:

## 2026-09-21 위험성 판단 기준을 회사 설정으로

- 위험성 수준 판단 기준(상·중·하의 정의와 허용 가능 경계)을 **회사 설정으로 올렸다.** 지금까지는 평가할 때마다 직접 타이핑했는데, 같은 회사인데 표준서마다 기준이 다르게 적힐 수 있었고 감사에서 "귀사의 판단 기준은 무엇입니까"에 한 문서로 답할 수 없었다.
- 위험성평가는 사업주가 기준을 **정해 두고** 그에 따라 실시하는 구조다. 원본은 회사에 하나, 평가는 생성 시점의 사본을 보관한다. `criteria_snapshot` 이라는 기존 컬럼 이름이 원래 그 의도였고 빠져 있던 원본을 `0013` 에서 채웠다.
- **과거 데이터는 소급되지 않는다.** 회사가 기준을 바꿔도 이미 승인된 평가는 자기 사본을 그대로 들고 있다. 평가 요청 시 서버가 그 시점의 회사 기준을 직접 읽어 스냅샷을 남기므로, 클라이언트가 보낸 값은 쓰지 않는다.
- 등급 수는 상·중·하 3단계로 스키마에 고정돼 있다(`initial_risk_level` CHECK). 회사가 정하는 것은 단계 수가 아니라 **각 단계의 의미와 허용 가능 경계**다. 같은 3단계라도 제조업과 건설업의 "상"은 다르다. 4단계 요구가 실제로 나오면 그때 등급을 데이터로 바꾸고 평가마다 등급표를 스냅샷하면 되며, 그 구조에서도 과거 평가는 자기 등급표로 렌더된다.
- 표준서 prefill 에서 `criteria` 를 뺐다. 회사 값이 원본이므로 표준서가 덮어쓸 값이 아니다. 작업지시 2번 단계는 회사 기준을 읽기 전용으로 보여 주고 회사정보 링크를 건다.
- 기본 문구를 컬럼 DEFAULT 로 넣어 기존 회사와 신규 회사가 같은 출발점을 갖는다.
- `company-settings.ts` 는 다른 서비스 모듈처럼 client 를 주입받는다. `./db` 를 물면 그쪽 `server-only` 가드가 딸려와 회귀 테스트가 `work-order-service` 를 import 할 수 없게 된다(실제로 한 번 깨졌다).
- 검증: lint·typecheck·build, DB 36, 첨부 8, e2e 8, 브라우저 17 통과. 마이그레이션 `0013` 적용 필요.

## 2026-09-21 요금 정책 재전환 — 인원 구간별 정액제

- 하루 전 "인원 한도 폐지 · 인당 과금" 결정을 되돌린다. **무료는 유지**하되 유료는 인당(1만원/인·월)이 아니라 **인원 구간별 월 정액**으로 바꾼다. 인당 과금은 인원이 늘수록 도입을 망설이게 하고, 구간 정액은 예측 가능한 고정비로 읽힌다.
- 구간(현재 재직 인원, **관리자 포함**): Basic ~19인 · Standard ~49인 · Pro ~99인. 100인 이상은 개별 협의로 구간표 밖에 둔다.
- 정가(VAT 포함) 55,000 / 132,000 / 242,000원, 출시 할인가 33,000 / 88,000 / 165,000원. **정가를 먼저 박고 할인으로 출시**해 나중에 할인 폭을 줄이는 방식으로 자연스럽게 인상한다. 가입 시점 가격은 12개월 보장한다.
- 할인율이 구간마다 다르다(40% / 33% / 32%). 화면에는 구간별 실제 할인율을 계산해 표시하고, 배지는 "최대 40%"로 둔다. 상수로 박으면 가격을 고칠 때 문구가 어긋난다.
- **세 구간의 기능은 모두 같다.** 무료/유료만 가른다. 덕분에 서버의 기능 게이트(`pro_state !== 'FREE'`)를 한 줄도 바꾸지 않았다 — 첨부·기록 조회·모니터링 전부 그대로다.
- 금액은 **공급가(VAT 별도)** 로 저장하고 화면에서만 VAT 포함가로 환산한다. 세금계산서에 공급가·부가세가 분리돼야 하기 때문이다.
- **상향은 Claude 구독과 같은 방식**: 남은 기간의 현재 요금을 크레딧으로 차감한 금액을 즉시 결제하고 **그날이 새 결제 기준일**이 된다. 다음 달부터 새 구간 요금이 온전히 청구된다. 하락은 다음 주기부터 적용하고 중도 환불은 없다. `upgradeQuote()` 가 크레딧·결제액·새 기준일을 계산한다.
- **계약 인원을 다 쓰면 인원 등록을 막는다.** 등록이 결제의 트리거다. 무료 회사에는 아무 이벤트도 없다 — 무료는 인원이 아니라 기능이 제한되므로 20인째든 200인째든 그대로 등록된다.
  - 처음에는 "막으면 그 작업자가 시스템 밖에 남아 TBM 기록에 구멍이 생긴다"는 이유로 안내만 하자고 제안했으나, 막지 않으면 결제 동기가 없다는 판단으로 차단으로 결정했다. 막히는 대상은 이미 유료 계약 중인 회사이고 상향 경로가 있다는 점이 근거다.
- 차단하려면 **계약 구간과 실제 인원을 분리**해야 한다. 구간을 인원에서 계산하면 인원이 늘 때 구간도 따라 올라가 초과 판정이 성립하지 않는다. `0012` 에서 `companies.plan` 과 `plan_started_at`(결제 기준일)을 추가했다.
- 차단 지점은 인원이 실제로 늘어나는 두 경로뿐이다 — 초대 수락(`acceptInvite`)과 가입 승인(`mutateMember approve`). 둘 다 `lockCompany()` 안에서 검사한다. 동시에 두 명을 승인하면 같은 인원 수를 읽어 상한을 넘길 수 있기 때문이다. 회사코드 가입 신청 자체는 막지 않는다 — 신청은 대기열에 남고 관리자가 승인할 때 걸린다.
- 결제(PG)가 없어 `plan` 을 바꿀 주체가 없으므로 운영자 화면에 요금제 변경을 넣었다. 입금 확인 후 구간을 올리면 등록이 다시 열리고 결제 기준일이 갱신된다. PG 도입 시 결제 완료가 이 역할을 대신한다.
- 기준 인원은 기존 `companies.active_headcount` 를 그대로 쓴다. 가입·퇴사 때 `refreshHeadcount()` 가 이미 갱신한다. 법적 개념인 `employee_size_band`(중대재해처벌법 판단용)와는 경계가 비슷해도 분리해 둔다 — 법이 바뀔 때 요금까지 흔들리면 안 된다.
- 결제(PG)는 이번 범위가 아니다. 구간 판정·차단·가격 표시·정산 계산까지 넣었고 `/billing` 은 여전히 문의 폼으로 연결된다. 얼리버드 보호 만료일·적용 단가를 회사별로 저장하는 구독 테이블은 결제 도입 시 함께 만든다(현재는 전역 상수로 판정).
- 코드: `plans.ts` 신설(구간·가격·할인율·상한·상향 정산), `membership-mutations.ts` 에 `seatCapacityError()`, `billing-view.tsx`·`members-view.tsx`·운영자 회사 상세 갱신. `PRO_PLAN`(인당 과금 상수) 제거.
- 검증: lint·typecheck·build, DB 회귀 36(좌석 상한 테스트 신규), 첨부 8, e2e 8, 브라우저 17 전부 통과. 마이그레이션 `0012` 적용 필요.

## 2026-09-21 PWA 설치 · 작업자 링크 토큰 · 알림 채널 설계

- PWA: manifest·아이콘·safe-area는 이미 있었고 service worker만 없어 Android 설치(WebAPK)가 불가했다. `public/sw.js` 추가로 해결. iOS는 기존 상태로 이미 설치 가능했고 실기기 확인됨.
- sw 캐시 전략은 보수적으로: `/api/*`와 타 출처(S3 presigned·OAuth)는 가로채지 않고, 빌드 해시가 박힌 `/_next/static`·`/brand`만 cache-first, 화면은 네트워크 우선 + 실패 시 `offline.html`. 로그인 기반 SaaS에서 회사별 데이터가 캐시에 남지 않게 하는 것이 설계의 본체다. registrar는 production에서만 등록.
- `next.config.ts`에 `/sw.js` `no-store` 추가, manifest에 `id` 추가(이후 start_url 변경 시 다른 앱으로 인식되는 문제 방지).
- 첨부 권한 정책 전환: 사진 첨부 가능 여부를 **역할이 아니라 요금제로만** 결정. 기존 `verifyActor`는 WORKER를 전면 차단했으나 위험 앞에 서 있는 사람이 작업자이므로 정책이 뒤집혔다. Free는 전 대상 업로드 불가(= 요금제 안내와 코드가 이제 일치), Pro는 작업자도 가능.
- 역할은 "첨부 가능 여부"가 아니라 "어떤 문서에 붙이는가"만 가른다 — `verifyTargetOwnership`이 테넌트만 검사하므로 작업자는 `work_order`·`inspection_finding`에만 허용. 작업자는 본인이 올린 첨부만 확정·삭제, 관리자는 회사 전체 정리 가능.
- 작업자 링크 접근: 현장은 인원 교체가 잦고 기기도 제각각이라 설치·로그인을 전제하면 도입이 막힌다. 토큰 링크로 무설치·무로그인 진입을 기본값으로 삼기로 결정. `src/server/worker-access.ts` — 발급·검증·열람기록·폐기.
- 토큰은 정보를 담지 않는 16바이트 임의 포인터(base64url 22자). JWT식으로 이름을 넣으면 문자 본문·로그·히스토리에 평문으로 남고 폐기가 불가능해지며 SMS 90바이트를 넘긴다. DB에는 sha256 해시만 저장.
- 배정별 1개, 공용 링크 없음 — 공용이면 "누가 TBM을 확인했는가"가 남지 않아 증빙이 성립하지 않는다. 무효화 조건: 폐기·만료·발급회차 불일치(재발급 시 옛 링크 사망)·지시서 취소·퇴사. `linkActor()`가 기존 `Actor`로 가는 유일한 통로이며 이후 권한 검사는 로그인 사용자와 동일하게 돈다.
- 증빙 수준은 "해당 연락처로 보낸 링크가 열렸고 확인이 눌렸다"까지. 본인 인증이 아니다. 이름 입력은 채택하지 않았다(토큰이 이미 배정별이라 서버가 누구인지 알고, 옆 사람도 이름은 알므로 강도가 오르지 않음) — 대신 이름을 표시하고 확인만 받는다. 고객 고지 필요.
- `0010`에서 토큰을 `work_order_outputs`에 붙였다가 `0011`에서 `work_order_access_grants`로 분리. Pro는 한 작업자에게 메일과 알림톡을 모두 보내 발송 기록이 채널별로 나뉘는데, 토큰까지 복제되면 열람 집계가 흩어진다. 접근 권한과 발송 기록은 수명도 다르다.

- 알림톡 템플릿은 사전 승인제이고 광고성 문구가 금지되므로 Pro 전환 유도는 앱 안에서만 한다. 열람 데이터(`open_count`·`first_opened_at`)가 그대로 전환 근거가 된다("메일 5건 발송 · 열람 0건").

- 검증: 타입·lint·프로덕션 빌드 통과, 첨부 회귀 8개 통과(작업자 시나리오 3개 신규). `0010`·`0011` 운영 Neon 적용 완료 — 두 파일은 이후 수정하지 않는다.

## 2026-09-20 표준서 모델 재정의 — flat mutable + 위험성평가 회차 이력

### 법적 근거

- **표준서(작업표준서)** — 산안법상 필수 문서가 아님. 사업장 자율 관리 문서. 인정 심사에서도 표준서 개정 이력이 심사 항목이 아님. 따라서 무거운 버전 관리 요건이 없음.
- **위험성평가** — 산안법 제36조 · 시행규칙 제37조. **법정 문서**, 실시 이력 3년 보존 의무. 최초/정기/수시/상시 각 회차가 독립 문서로 남아야 함.

두 문서 성격이 다르므로 스키마도 다르게 취급.

- `risk_assessments.standard_version_id` 삭제

**추가**:

- `standards.ptw_required` (버전에서 표준서 직접으로 이관)
- `standard_steps.standard_id` (직접 참조), UNIQUE (standard_id, order_no)
- `standard_checklist_items.standard_id` (직접 참조), UNIQUE (standard_id, category, order_no)
- `risk_assessments.standard_id` (nullable — NULL 은 간이평가/예외 경로)
- 인덱스 `risk_assessments_standard_performed_idx` (표준서별 최신 승인 평가 조회 가속)

**백필**: 기존 데이터의 `standard_versions` → `standards` flat 이전 후 구 컬럼·테이블 정리.

### 최종 관계

```
standards                       ← mutable, 단일 문서
  id, name, ptw_required, status (DRAFT/APPROVED/ARCHIVED)
  ─ 편집 이력은 audit_logs (before/after) 로 소명

standard_steps          ─ standard_id FK
standard_checklist_items ─ standard_id FK

risk_assessments               ← 회차별 이력, 시계열 축적
  id, standard_id (nullable), assessment_kind (FIRST/PERIODIC/AD_HOC/CONTINUOUS)
  performed_on, status (APPROVED/…)
  ─ 한 표준서에 여러 행 축적

work_orders
  standard_id      ← 어떤 표준서 기반인지
  risk_assessment_id ← 발급 시 사용한 특정 회차의 스냅샷 소스
```

### 실무 시나리오

**표준서 수정** — 관리자가 편집 화면에서 텍스트 수정 → 즉시 반영. 변경 이력은 `audit_logs`. 기존 발급된 지시서는 발급 당시 스냅샷을 이미 갖고 있어 영향 없음.

**정기평가 사이클** — 매년 표준서 상세 화면에서 "평가 회차 추가" → 유형 "정기평가" 선택 → 실시일·판단기준·위험요인·참여자 입력. 새 회차가 승인되어 지시서 발급 스냅샷 소스로 승격.

**수시평가** — 시설·물질·인력 변경, 사고 발생 시 표준서 그대로 두고 회차만 추가 (유형 "수시평가").

**만료 알림** — 표준서 상세에 유효기간 만료 시 상단 경고 배너, 지시서 발급 진입 불가.

### 확인된 한계 · 후속

- 표준서 수정 이력은 `audit_logs` before/after 로만 남음. UI 로 diff 조회는 향후 감사 로그 화면 개발 시 함께.
- 평가 회차 삭제·수정은 미지원 (법정 이력 보존). 실수 시 새 회차로 덮음.
- 표준서 폐기 시 그 표준서의 평가 이력은 남지만 새 지시서 발급 대상에서 제외.
- 표준서를 활성화하려면 최소 1개의 유효 승인 평가 필요.

- 기존 globals.css 수정은 보존. 신규 업무 기능·과금 상태 자동 전환·감사 로그는 이번 범위에 포함하지 않음.
- 실행 방법과 운영 보정 주의사항: [regression-testing.md](regression-testing.md).

### 6. 인프라 · 배포

**프로덕션 스택**

- AWS Lightsail Ubuntu 22.04 LTS · 서울 리전 · 고정 IP
- 도메인: **smbe.net** (Cloudflare Registrar 구매, DNS-only 회색 구름)

- DB: Neon Postgres (로컬↔프로덕션 단일 인스턴스, 1인 개발 전제)
- Compose 파일: `compose.yaml` (프로덕션), `compose.dev.yaml` (로컬)

**보안 · 접근**

- GitHub 리포지토리 private 전환
- 서버는 Ed25519 SSH deploy key 로 pull-only 액세스
- `.env` 는 서버 로컬 파일로 유지 (git 미포함)
- OAuth 콜백 URL `https://smbe.net/api/auth/callback/{google|naver|kakao}` 등록 완료

**배포 스크립트 (`scripts/`)**

- `deploy.sh` — git pull → 이미지 rebuild → healthy 체크 → 도메인 응답 확인
  - 옵션: `--no-pull`, `--logs`
- `status.sh` — 컨테이너 상태 + 로컬/공개 헬스체크 + 최근 로그 20줄
- `logs.sh [app|proxy]` — 실시간 로그 tail
- 심볼릭 링크로 전역 단축어: `smbe-deploy`, `smbe-status`, `smbe-logs`

**Cloudflare Email Routing**

- `hi@smbe.net → gooddonutsyh@gmail.com` 자동 포워딩 (수신 전용)
