# 작업지시 1차 구현

## 제공 흐름

홈의 **오늘의 작업 지시하기** 또는 **작업지시 → 작업 지시하기**에서 시작한다.

1. 작업명·방법·조 이름·PTW 필요 여부 입력
2. 간이평가: 실시일·구분, 판단 기준, 위험요인/수준/허용 여부/대책, 사전조사 정보, 실제 참여자 입력
3. 작업기간·시작/종료시간·장소·작업자 배정
4. TBM·작업 중 체크리스트 입력 후 임시저장
5. 상세에서 **평가 승인 후 발급**: 관리자 본인 승인 허용. 검토 확인 후 평가 승인과 발급을 하나의 트랜잭션으로 처리
6. 배정 인원 이메일 링크 전달, 지시서 QR 열람·인쇄/PDF 저장
7. 발급 후 현재 작업회차에서 TBM 또는 작업 중 점검 입력
8. 부적합 발생 시 지정 관리자 조치완료, 다음 회차 TBM에서 조치 내용 재확인

다른 관리자의 평가 검토를 원하는 경우 **평가 검토 요청 → 위험성평가 승인 → 작업지시 발급**도 가능하다.
지시서 자체의 별도 승인 절차는 없다. 본인 승인 여부는 평가 승인 감사 이력에 기록하며 PTW 자가 승인과 구분한다.

## 구현한 화면

- /work-orders: 전체·예정/진행·작성 중, 작업명 검색, 페이지 이동
- /work-orders/new: 네 단계 작성·임시저장·복사
- /work-orders/[id]: 작업 정보·평가·체크리스트·배정·승인/발급·QR·전달 상태·취소·변경 이력
- /work-orders/[id]/edit: 작성 중인 지시서 편집
- 로그인한 홈: 실제 예정·진행 작업. 비로그인 홈은 예시 데이터 표시

작업자는 배정된 발급 작업만 확인할 수 있다. 같은 회사의 활성 관리자만 작성·변경·발급할 수 있다.
작업자가 QR/링크를 열면 로그인 후 해당 지시서로 돌아간다.
무료 회사의 최근 1주일보다 오래된 종료·취소 기록은 건수만 표시하고 직접 상세 URL 접근도 차단한다.
작성 중 또는 발급·진행 중인 작업은 과거 기록 제한에서 제외한다.

## TBM·작업 중 점검

발급 시 작업기간의 각 작업일을 `work_sessions`로 생성한다. 야간작업도 시작일 기준 한 회차이며, 시작 2시간 전부터 종료 2시간 후까지 입력할 수 있다.

- TBM은 배정 작업자별 1회 확인이 필요하고, 위험요인·감소대책을 먼저 보여준다.
- 작업 중 점검은 배정 작업자·관리자가 수행할 수 있고 같은 회차에 여러 번 입력할 수 있다. TBM 미확인 상태에서도 입력 가능하다.
- 점검 결과는 적합·부적합·해당없음과 코멘트로 저장하며, 입력자 역할·저장시각·QR/링크/웹 진입경로를 보존한다.
- 부적합마다 현재 회사의 관리자를 지정하고, 지정 관리자만 조치 내용을 입력해 종결할 수 있다. 작업 종료·취소가 부적합을 자동 종결하지 않는다.
- 이전 회차에서 종결된 조치 내용은 다음 TBM 시작 전에 표시한다.
- 관리자는 `/inspections`에서 자신에게 배정된 미조치 부적합을 확인한다. 무료 이용의 과거 점검 열람 제한과 무관하게 미조치 항목은 계속 조치할 수 있다.
- 사진 첨부, 관리자 사후입력, 저장 결과 수정·이력은 후속 범위다.

## 데이터와 동시 요청

db/0003_work_orders.sql은 신규 테이블만 추가한다. 기존 테이블·행 삭제는 없다.

- risk_assessments / risk_assessment_items / risk_assessment_participants
- work_orders / work_order_assignments / work_order_snapshots / work_order_checklist_items
- work_order_outputs: 이메일 전달 대기·발송·실패·재시도 기록
- audit_logs: 작업지시 생성·수정·평가 요청/승인·발급·취소·링크 전달 이력

회사 행 잠금 후 현재 관리자 권한과 소속을 재확인한다. revision으로 오래 열린 편집 화면의 덮어쓰기를 막는다.
발급은 평가·지시서·배정·체크리스트·전달 대기 기록을 같은 트랜잭션으로 확정한다.
발급 실패 시 본인 승인도 함께 롤백한다. 이메일 전송은 커밋 후 실행하며 실패해도 발급 결과는 유지한다.
같은 요청을 동시에 발급하면 한 건만 성공한다.

발급 시 평가·작업방법은 JSON 스냅샷으로, 체크리스트와 배정 이름은 별도 행으로 보존한다.
작성 중 내용을 저장하면 연결된 평가 승인을 해제하고 다시 검토하도록 한다. 이전 평가 원문은 삭제하지 않는다.
복사는 작업기간·승인·발급·점검 이력을 초기화하고 현재 활성 인원의 배정만 유지한다.
원본 지시서 ID는 복사본에 저장하지 않는다.

한국시간으로 일정 상태를 조회 시 계산한다. 야간조의 종료시간은 다음 날로 계산하며 최대 16시간이다.
작업기간은 1차 구현에서 최대 366일, 기간 내 매일 같은 시간으로 처리한다.
첫 회차 시작 2시간 전부터 마지막 회차 종료 2시간 후까지 진행 상태로 표시한다.
기간 종료는 안전조치 완료를 의미하지 않는다.

## 이메일 설정과 전달

APP_URL에 실제 접속 주소, RESEND_API_KEY와 EMAIL_FROM에 발송 설정을 입력한다.
발급 시 배정자의 이메일을 전달 기록에 보관하고 링크를 보낸다.
이메일 주소나 설정이 없으면 미전달 상태를 표시하며 링크 복사/QR로 직접 전달할 수 있다.
발송 완료 표시는 메일 서비스 접수 성공을 의미한다.

한 번에 최대 50명, 미전달 재시도는 1분 간격이다. 5분 이상 멈춘 전송은 재시도할 수 있다.
동시 재전송은 행 잠금으로 제어하며 메일 서비스에 동일 전달 기록의 idempotency key를 보낸다.
50명을 넘으면 상세의 **미전달 링크 다시 보내기**로 나머지를 전달한다.
독립적인 메일 재시도 스케줄러와 SMS는 아직 없다.

현재 전달 링크는 `/work-orders/<id>?via=link`로 **로그인이 필요하다.**
작업자가 로그인 없이 진입하는 토큰 링크는 `db/0010_work_order_access_tokens.sql`과
`src/server/worker-access.ts`에 토대만 들어가 있고, 화면과 발송 전환은 아직이다.
전달 채널은 요금제로 가른다 — **무료는 메일, 유료는 메일+알림톡(실패 시 SMS).** 토큰 자체는 채널과 무관하다.
설계와 보안 경계: [worker-access.md](worker-access.md).

## 이번 범위에 없는 항목

- PTW 신청·승인: 필요로 설정한 지시서는 저장할 수 있지만 발급을 차단
- 표준서 연계 및 검토된 업종별 템플릿: 현재는 직접입력 간이평가
- 발급 후 일정·인원 변경(W-04), 작업 없는 날 제외, 조별 일괄 생성
- 회사 위험성 판단 기준의 버전 마스터, 평가 회차 집계, 평가 별도 메뉴
- 사고 등록, 점검 결과 보고서, S3 첨부, SMS

평가·PTW가 모두 완성된 것으로 표시하지 않는다. TBM·작업 중 점검의 기본 제출과 부적합 조치는 구현됐지만, 사진·사후입력·수정이력은 아직 후속 범위다.

## 실행·검증

기존 Docker 실행 명령을 그대로 사용한다. 별도 API 서버나 상시 로컬 개발 DB는 추가하지 않는다.
새 환경에서는 npm run db:migrate로 0004까지 적용해야 점검 화면과 부적합 알림함을 사용할 수 있다.
이번 연결된 Neon DB에는 0004가 이미 적용됐다. 앱 운영 배포는 별도다.

기본 검증:

```sh
npm run lint
npm run typecheck
npm run build
npm run test:e2e
```

실제 SQL 및 로그인 화면 흐름 검증에는 일회성 PostgreSQL 컨테이너를 사용한다.
이미 55439 포트를 사용하는 테스트 컨테이너가 있으면 새로 만들지 말고 재사용한다.

```sh
docker run --detach --rm --name smbe-regression -e POSTGRES_PASSWORD=smbe-test-only -e POSTGRES_DB=smbe_regression -p 127.0.0.1:55439:5432 postgres:16-alpine
docker exec smbe-regression pg_isready -U postgres
npm run test:db
npm run test:orders-ui
docker stop smbe-regression
```

test:orders-ui는 시크릿을 제외한 임시 복사본을 빌드하고, 복사본의 DB 연결만 로컬 PostgreSQL로 바꾼다.
테스트용 서명 세션 쿠키를 사용하되 앱의 실제 권한 검사와 Server Action을 실행한다.
운영 소스에는 테스트 인증 우회나 로컬 DB 분기 코드가 들어가지 않는다.
테스트 스키마는 종료 시 제거되며 스크린샷·trace는 출력된 임시 디렉터리에 남는다.
실제 OAuth 제공자 로그인 및 실제 이메일 수신 확인은 이 자동 검증 범위 밖이다.
