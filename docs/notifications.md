# 작업자 알림 발송 설계 (알림톡 + SMS 대체발송)

작업지시를 발급하면 배정된 작업자에게 링크를 보낸다. 그 링크가 실제로 도달해야 TBM·점검이
돌아가므로, 도달률이 이 제품의 급소다. 링크 자체의 구조는 [worker-access.md](worker-access.md)에 있다.

## 채널 매트릭스

| 요금제     | 채널                                 | 성격                                                         |
| ---------- | ------------------------------------ | ------------------------------------------------------------ |
| **무료**   | 메일 + 화면 QR                       | 대면 배포는 화면의 QR 을 보여 주는 것으로 한다. 인쇄물(A4)은 유료 |
| **유료**   | 메일 + **알림톡 → 실패 시 SMS 대체** | 흩어진 현장·시간차 작업의 원격 배포                          |

구간(Basic·Standard·Pro)은 채널을 가르지 않는다. 무료/유료만 가른다.

출력물(A4 한 장)은 유료로 옮겼다(v5.8). 무료도 화면의 QR 을 보여 주면 대면 배포는 되지만,
작업 장소에 붙여 두는 게시물은 유료에서만 나온다.

무료를 "안 되는 제품"으로 두지 않는 것이 요점이다. 무료 구간에서 업무가 완결되지 않으면
유료 전환이 아니라 이탈이 된다. 무료는 대면 배포로 완결되고, 유료는 **도달 채널을 추가**한다.

안전 알림을 요금제로 막는다는 인상을 주면 중대재해 맥락에서 평판 위험이 있다. 마케팅 문구도
"유료여야 알림이 간다"가 아니라 "유료는 현장에 흩어져 있어도 전달된다"로 쓴다.

## 왜 알림톡 단독이 아니라 SMS 대체발송을 묶는가

알림톡이 SMS보다 싸고 확인율도 높지만, **카카오 계정이 없으면 도달하지 않는다.**

- 고령 작업자
- **외국인 노동자** — 건설현장 비중이 크다

안전 알림에서 "일부에게 안 갔다"는 사고다. 그래서 알림톡은 기본 채널이고 SMS는 안전망이다.
대부분 싼 알림톡으로 나가고 일부만 SMS로 빠지므로 비용과 도달을 동시에 잡는다.

## 대체발송은 발송사가 처리한다

앱이 "알림톡 실패 감지 → SMS 재발송" 루프를 직접 만들지 않는다. 국내 발송사들은 알림톡 요청에
대체발송 옵션을 함께 받아 실패 시 자동으로 SMS/LMS를 보낸다.

```
앱 → 발송사 [알림톡 + 대체발송 설정]
        ├─ 성공 → 알림톡 도달
        └─ 실패(미설치·차단·수신거부) → 발송사가 SMS 자동 발송
앱 ← 결과 [실제 나간 채널 + 메시지 ID + 결과 코드]
```

**앱 입장에서는 요청 1건이고, 결과에서 어느 채널로 나갔는지를 받아 기록한다.** 재시도 로직을
두 겹으로 만들지 않는 것이 이 설계의 핵심이다.

## 운영 제약 (알림톡)

| 항목             | 내용                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------ |
| 템플릿 사전 승인 | 카카오 심사를 거친 템플릿만 발송. 본문 고정, 변수만 치환. 작업지시명·일시·장소를 변수로 설계한다 |
| 발신프로필       | 카카오톡 채널 개설 + 사업자 인증                                                                 |
| 광고성 금지      | 정보성만 허용. **유료 전환 유도 문구는 넣을 수 없다** — 전환 유도는 앱 안에서만 한다            |
| 친구 추가        | 불필요. 전화번호 기반이라 채널 친구가 아니어도 발송된다                                          |
| 링크 도메인      | 템플릿 심사 시 등록한 도메인만 사용 가능                                                         |

## SMS 대체발송 시 길이

SMS는 90바이트를 넘으면 LMS로 전환되어 단가가 오른다. 토큰 링크를 `/w/<22자>`로 짧게 잡은
이유가 여기 있다 (계산: [worker-access.md](worker-access.md)). **알림톡 템플릿과 SMS 대체 문구는
길이 예산이 다르므로 따로 설계한다.**

## 데이터 모델 — 해결해야 할 충돌

현재 `work_order_outputs`는 `UNIQUE (work_order_id, issue_version, user_id)`라 **한 사람당 1행**이고,
`0010`에서 접근 토큰을 이 행에 붙였다.

그런데 유료는 한 사람에게 **메일과 알림톡을 모두** 보낸다. 채널별 발송 결과(성공·실패·재시도·
메시지 ID)를 남기려면 채널마다 행이 필요하다. 그러면 토큰이 채널 수만큼 중복된다.

**토큰은 채널의 것이 아니다.** "이 작업자 × 이 작업지시 × 이 발급회차"의 것이고, 메일로 가든
알림톡으로 가든 같은 링크여야 열람 집계가 하나로 모인다.

### 권장: 관심사를 분리한다

| 테이블                            | 책임                                          | 단위                         |
| --------------------------------- | --------------------------------------------- | ---------------------------- |
| `work_order_access_grants` (신규) | **접근 권한** — 토큰 해시·만료·폐기·열람 기록 | 작업지시 × 발급회차 × 작업자 |
| `work_order_outputs` (기존)       | **발송 기록** — 채널·상태·재시도·메시지 ID    | 위 + 채널                    |

수명도 다르다. 토큰은 작업 기간 동안 살아 있고, 발송 기록은 시점의 사실이다.

`work_order_outputs`에 추가할 컬럼 (발송 구현 시점에 `0012`로):

| 컬럼                   | 용도                                                                             |
| ---------------------- | -------------------------------------------------------------------------------- |
| `link_channel`         | 요청 채널 (`EMAIL` / `ALIMTALK`). 기존 컬럼, UNIQUE에 포함시킨다                 |
| `delivered_channel`    | **실제 나간 채널** (`EMAIL`/`ALIMTALK`/`SMS`/`LMS`). 대체발송 결과가 여기 남는다 |
| `provider_message_id`  | 발송사 메시지 ID. 장애 추적과 정산 대조용                                        |
| `provider_result_code` | 실패 원인 코드 원문                                                              |

### 미결정

- ~~0010의 토큰 컬럼을 어떻게 옮길 것인가~~ → **`0011`에서 분리 완료.** 러너가 0010 → 0011
  순서로 적용하므로 0010의 운영 적용 여부와 무관하게 결과가 같다.
- **발송사 선정** — 솔라피·알리고·NHN Cloud·네이버 SENS 등. 대체발송 API 계약이 조금씩 달라
  `provider_*` 컬럼의 형태가 발송사 선택에 따라 달라진다.
- 휴대폰번호 수집·이용 동의 문구와 보관 정책 (`users.phone`은 이미 있다)
- 유료 요금제의 월 발송량 상한 — SMS는 건당 변동비라 무제한이면 대량 발송 고객에서 마진이 깎인다

## 어느 주소로 보내는가

`users` 에 메일이 두 개 있다.

| 컬럼 | 뜻 | 누가 정하나 |
| --- | --- | --- |
| `email` | **로그인 계정의 메일** | 소셜 로그인에서 따라온다. 사람이 고치지 않는다 |
| `contact_email` | **알림 받을 주소** | 가입 화면과 마이페이지에서 본인이 정한다 (`0018`) |

카카오 로그인에 딸려온 개인 주소가 아니라 회사 메일로 받고 싶은 경우가 많아
둘을 나눴다. 보내는 자리는 전부 **`COALESCE(contact_email, email)`** 을 쓴다 —
지시서 링크(`work_order_outputs.link_target`), 가입 신청 알림, 주간 회의 알림.
따로 정하지 않은 사람은 예전과 똑같이 로그인 계정 메일로 받는다.

로그인은 `user_identities` 로 하므로 `contact_email` 을 바꿔도 로그인은 그대로다.
반대로 `users.email` 은 부분 유일 인덱스와 provider 병합 규칙이 매여 있어 건드리지
않는다.

**휴대폰은 가입할 때 선택으로 받아 둔다.** 알림톡·SMS 는 아직 붙이지 않았지만
(아래 §구현 순서 1~2), 번호는 그때 가서 다시 받으러 다니기 어렵다. 가입 화면에서
"나중에 문자·알림톡으로도 받는다" 고 알리고 받아 둔다. 안 넣어도 가입된다 —
여기서 막으면 정작 현장에 들어가야 할 사람이 문턱에서 걸린다.

## 관리자 메일 — 미실시 회의 알림

작업자 링크와 별개로, **관리자에게 가는 메일**이 하나 있다. 주가 끝났는데 안전점검 회의
기록이 없으면 **관리감독자와 안전관리자**에게 한 번 알린다.

| 항목 | 내용 |
| --- | --- |
| 대상 | `MANAGER_SUPERVISOR` · `MANAGER_SAFETY` (ACTIVE, 메일 있는 사람) |
| 시점 | 주가 끝난 뒤. 진행 중인 주는 아직 미실시가 아니다 |
| 횟수 | 주당 **한 번**. `safety_meeting_reminders` 의 유일 제약이 보장한다 (`0016`) |
| 묶음 | 회사당 메일 **한 통**에 밀린 주를 나열한다 |
| 요금제 | 가르지 않는다. 안전 알림을 유료 기능으로 두면 중대재해 맥락에서 평판 위험이 있다 |

작업자에게는 보내지 않는다. 회의를 실시할 책임이 없는 사람에게 알리면 자기가 할 수 없는
일을 통보받는 셈이 된다.

**앱 안에 스케줄러를 두지 않는다.** 컨테이너가 여러 개로 늘어나면 각자 타이머를 돌려 같은
메일을 여러 번 보낸다. 호스트 cron 이 **매일** `POST /api/cron/meeting-reminders` 를 때리고
(`CRON_SECRET` 인증), 중복 방지는 DB 가 맡는다. 매일 도는 이유는 주가 끝났는지를 앱이
한국시간으로 판정하기 때문이다 — cron 시각은 도착 시간만 정하고, 하루 놓쳐도 따라잡는다.
설치는 서버에서 `./scripts/setup-cron.sh` 한 줄이다 ([operations.md](operations.md) §3).

발송 실패도 장부에는 기록한다. 실패했다고 매번 다시 보내면 같은 주를 반복해 알리게 되고,
그건 알림이 아니라 소음이다.

## 관리자 메일 — 가입 신청 알림

회사코드로 가입을 신청하면 `company_members` 에 `JOIN_PENDING` 행이 하나 생길 뿐이다.
관리자가 인원관리 화면을 직접 열어 보기 전에는 신청이 있는 줄도 모르고, 신청한 사람은
기다리다 결국 전화를 건다. **승인 전에는 작업에 배정할 수 없으므로**(§14-1 `JOIN_PENDING`
= 후속 업무 불가) 기다리는 동안 그 사람은 현장에 투입되지 못한다. 그래서 두 곳으로 알린다.

| 항목 | 내용 |
| --- | --- |
| 대상 | `MANAGER_SUPERVISOR` · `MANAGER_SAFETY` (ACTIVE, 메일 있는 사람). 승인 권한이 있는 사람만 |
| 시점 | 신청이 저장된 직후 1회 |
| 링크 | `/company/members` — 승인 대기가 있으면 그 탭이 먼저 열린다 |
| 요금제 | 가르지 않는다 |
| 화면 | 홈에 **"가입 승인 대기 N명"** 한 줄. 메일은 묻히고, 관리자가 매일 여는 화면은 홈이다 |

**발송 실패가 가입을 막지 않는다.** 신청은 이미 저장됐고 메일은 거들 뿐이라, 발송은
트랜잭션 밖에서 `try/catch` 로 감싼다 — 지시서·PTW 발송과 같은 규칙이다. 메일이 실패해도
홈의 한 줄은 남으므로 신청이 사라지지는 않는다.

초대 링크로 들어온 사람은 승인 없이 바로 `ACTIVE` 가 되므로(§14-1) 이 메일이 나가지 않는다.
알릴 것이 없다.

작업자에게는 보내지 않는다. 승인은 관리자만 할 수 있다.

## 전환 동선과의 연결

`work_order_access_grants`의 열람 데이터(`open_count`, `first_opened_at`)는 그대로 **무료 → 유료
전환 근거**가 된다. 토큰이 발송 기록에서 분리됐으므로(`0011`) 열람 집계는 채널이 몇 개든
작업자 한 명당 한 줄로 모인다.

```
작업지시 #123 전달 현황
  메일 발송 5건 · 열람 0건
```

"문자가 좋습니다"라는 주장이 아니라 "당신 회사에서 아무도 열지 않았습니다"라는 데이터가 된다.
토큰 링크는 채널과 무관하게 열람을 측정하므로 메일·알림톡·SMS를 같은 지표로 비교할 수 있다.

**이 유도 문구는 앱 안에만 둔다.** 알림톡 본문에 넣으면 광고성으로 분류되어 템플릿이 반려된다.

## 구현 순서

1. 발송사 선정 → 대체발송 API 계약 확인 — **미완**
2. 카카오톡 채널 개설 · 발신프로필 등록 · 템플릿 심사 제출 (영업일 소요) — **미완**
3. ~~토큰 테이블 분리 마이그레이션~~ — **완료** (`0011`)
4. ~~링크를 토큰 URL로 전환~~ — **완료**. 채널별 발송으로의 확장은 1번에 달려 있어 미완
5. ~~`/w/<토큰>` 화면~~ — **완료**
6. 전달 현황(발송·열람) 표시 — 미완

2번이 외부 심사라 가장 오래 걸린다. **1~2번을 먼저 걸어두는 것이 여전히 병목이다.**
현재는 채널이 메일 하나뿐이고, 그 메일이 나르는 링크는 이미 토큰 링크다.

## 웹 푸시 — 공지·자료실 (유료)

통합자료실(공지사항·자료실)의 글을 **처음 발행**할 때 유료 회사의 구성원 기기로
웹 푸시를 보낸다. 무료 회사는 보내지 않는다. 다시 저장해도 두 번 보내지 않는다
(`board_posts.push_sent_at`).

- 구독은 기기 단위다 (`push_subscriptions`, endpoint 가 기기·브라우저를 특정).
  회사에 묶지 않고, 보낼 때 `company_members` 로 대상을 고른다. 작성자는 뺀다.
- 켜는 곳: 홈 맨 위 안내(유료 회사 구성원, 한 번 닫으면 그 기기에서는 다시 안 뜸)와
  마이페이지. iPhone 은 홈 화면에 추가한 아이콘으로 열어야 켤 수 있다 (iOS 제약).
- 받는 곳: `public/sw.js` 의 `push` 가 알림으로 띄우고, `notificationclick` 이 그
  글을 연다.
- 만료된 구독(404·410)은 보내다가 지운다. 실패는 발행을 막지 않는다 (메일과 같은
  규칙).
- 키: `VAPID_PUBLIC_KEY`·`VAPID_PRIVATE_KEY`·`VAPID_SUBJECT`. 없으면 `skipped` 로
  건너뛴다. 코드: `src/server/push.ts`, `src/features/push/`.
